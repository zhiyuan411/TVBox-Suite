# TVBox-Suite

TVBox-Suite 是一个自用定制版 TVbox 项目，包含专属源管理页面、TVbox 资源整合处理脚本等周边工具，纯个人定制使用。

该项目不仅提供了基于 TVbox 的增强改进（主要是防御性编程的健壮性提升）的定制版本，还构建了一套完整的 TVBox 源管理系统，通过 `script` 和 `web` 目录的工具实现视频源的批量管理、优化处理和自动化运维。

## 项目特点

- 支持多种视频源
- 内置多种播放器（系统播放器、IJK播放器、Exo播放器）
- 支持搜索功能
- 边看边搜：搜索过程中可直接点开视频观看，返回后搜索不中断、结果继续累积
- 搜索并发可自定义：适配手机与电视/盒子的不同性能
- IJK 播放器卡死自愈：长时间卡顿自动重连，减少手动切换源的次数
- 播放缓冲可自定义：内存缓冲上限可调，暂停后仍会继续填充到该水位（native 上限 15MB）
- 缓存大小实时可见：播放器右上角网速后显示当前内存缓存大小，验证缓冲行为更直观
- 播放码率实时可见：IJK 播放器左上角在分辨率之后显示当前平均码率，m3u8、TS、MP4 等常见格式均可显示
- 支持历史记录
- 支持 DNS 配置
- 支持多版本构建（normal 和 python 版本）

## 版本差异

### normal 版本
- **功能**：提供基础的视频播放和搜索功能
- **体积**：体积较小，适合对应用大小有要求的场景
- **性能**：启动速度快，运行流畅
- **适用场景**：日常视频播放，不需要 Python 爬虫功能的用户

### python 版本
- **功能**：包含 normal 版本的所有功能，同时支持 Python 爬虫
- **体积**：体积较大，包含 Python 运行时环境
- **性能**：启动速度略慢，但功能更丰富
- **适用场景**：需要使用 Python 爬虫功能的用户，对功能完整性有要求的场景

## 核心组件

### 构建脚本 (build_apk.sh)

`build_apk.sh` 是项目的核心构建脚本，提供了完整的编译和打包流程：

- **功能**：
  - 自动检测和配置 Java 环境
  - 清理之前的构建产物（可选）
  - 编译并构建 debug 版本的 APK
  - 自动复制构建产物到 web 目录
  - 提供友好的构建过程输出

- **构建流程**：
  1. 检查当前 Java 环境
  2. 清理之前的构建（如果指定 --clean 参数）
  3. 编译并构建 debug 版本的 APK
  4. 检查构建结果并显示生成的 APK 文件
  5. 复制 APK 文件到 web 目录

- **产物管理**：
  - `tvbox.apk`：Python 版本（arm64）
  - `tvbox-old.apk`：Python 版本（armeabi）
  - `tvbox2.apk`：Normal 版本（arm64）
  - `tvbox2-old.apk`：Normal 版本（armeabi）

- **使用方法**：
  ```bash
  # 清理并构建
  ./build_apk.sh --clean
  
  # 增量构建
  ./build_apk.sh
  ```

## TVBox 源管理系统

`script` 和 `web` 目录共同组成了一个独立的 TVBox 源管理系统，提供了完整的视频源管理解决方案：

### 系统架构

- **前端管理界面**：通过 `web/s.html` 提供用户友好的管理界面
- **后端处理**：
  - `merge-sources` 脚本：处理和合并视频源
  - `random-sites` 脚本：优化站点排序
- **存储**：`web` 目录作为资源存储和服务目录

### 核心功能

1. **批量源管理**：
   - 通过 `s.html` 管理界面，支持批量输入多行视频源
   - 系统会根据无效历史自动去重后添加到输入文件

2. **源处理和优化**：
   - `mergeSources.3.0.py` 脚本将输入文件的源整理为 TVBox 所需的源文件
   - 支持频道聚合、分组管理、频道排序等功能
   - 生成多种格式的输出文件，满足不同需求

3. **站点排序优化**：
   - `randomSites.py` 提供对 TVBox 源的站点排序（白名单+随机+黑名单）
   - 解决源数量大时搜索结果很慢以及搜索结果不理想的问题

4. **自动化运维**：
   - 支持通过定时触发，根据访问情况自动执行
   - 定时任务配置可参考 `samples/crontab.sample`

5. **Web 服务集成**：
   - 通过 web 服务提供视频源访问
   - Web 服务配置可参考 `samples/nginx.conf.sample`
   - 后端 API 实现可参考 `samples/api.py.sample`

### 使用流程

1. **输入源**：通过 `s.html` 界面批量输入视频源
2. **处理源**：运行 `mergeSources.3.0.py` 脚本处理输入文件
3. **优化源**：运行 `randomSites.py` 脚本优化站点排序
4. **部署服务**：配置 web 服务提供源访问
5. **自动化维护**：设置定时任务自动执行源处理和优化

### 技术优势

- **高效管理**：批量处理和自动去重，提高源管理效率
- **智能优化**：通过白名单+随机+黑名单机制，优化搜索结果
- **易于部署**：提供完整的配置示例，方便快速部署
- **稳定可靠**：验证和过滤无效源，提升应用稳定性
- **扩展性强**：模块化设计，易于添加新功能和适配新需求

### 应用场景

- **源数量大**：当视频源数量众多时，通过排序优化提升搜索速度和质量
- **维护成本高**：通过自动化处理和定时任务，减少人工维护成本
- **源质量参差不齐**：通过验证和过滤，提升整体源质量
- **多设备使用**：通过 web 服务，为多台设备提供统一的源访问

## 核心修改

- **搜索功能优化**：通过防御性编程提升搜索功能的健壮性
- **边看边搜**：搜索过程中点开视频观看，返回后搜索会自动继续，之前已搜到的结果不会丢失，剩余结果继续补齐
- **快速搜索体验修复**：修复快速搜索模式下从视频详情返回后搜索不再继续的问题
- **搜索并发可调**：新增“搜索并发数”“插件搜索并发数”、“总并发上限”、“单域名并发上限”、“快速搜索批次大小”设置项，手机可调高提速、电视/盒子可保持默认以保证稳定
- **搜索清理优化**：移除搜索过程中无实际收益的强制内存回收，减少搜索卡顿
- **IJK 卡死自愈**：当播放长时间无速度、位置停滞超过阈值时自动重建连接、保留进度续播，避免需要手动切换源；同一播放会话最多自动恢复 3 次，阈值可在设置中调整
- **播放缓冲可调**：新增“缓冲大小”设置项（默认 15MB，可调 2/4/8/15MB），暂停后会继续填充到该水位
- **缓存大小可见**：播放器右上角在网速之后实时显示当前内存缓存大小（MB，保留 2 位小数），便于观察缓冲水位与暂停缓存是否生效
- **播放码率可见**：IJK 播放器左上角在分辨率之后实时显示当前平均码率（Mbps，保留 2 位小数）。码率按已缓冲内容的实际数据量换算，属于一段时间内的平均码率，因此对 m3u8 的多切片、单切片、变码率以及 TS、MP4 等格式都能给出接近真实的值；取不到码率的源会自动隐藏该项，不影响原有分辨率显示。Exo 播放器在能读取到轨道信息时也会一并显示
- **磁盘缓存可调**：原“IJK 缓存”开关升级为“磁盘缓存上限”（默认 2GB，可设为 0 关闭），让 mp4/mkv/avi 直链可“边播边存整集”、复看更快
- **代码结构优化**：调整项目结构，提高代码可维护性
- **构建系统优化**：简化构建配置，提高构建效率

### 搜索性能设置

设置页系统区新增了 **搜索性能** 设置项（点击后弹出独立弹窗），把与搜索速度相关的参数集中在一处，共 5 项，默认值均为最保守的档位：

| 选项 | 默认值 | 可选值 | 生效时机 |
|---|---|---|---|
| 搜索并发数 | 5 | 5 / 8 / 16 / 32 | 下次搜索 |
| 插件搜索并发数 | 5 | 5 / 8 / 16 / 32 | 下次搜索 |
| 总并发上限 | 64 | 64 / 128 / 256 / 512 | 需重启 |
| 单域名并发上限 | 5 | 5 / 8 / 16 / 32 / 64 | 需重启 |
| 快速搜索批次大小 | 50 | 50 / 100 / 200 / 500 / 1000 | 下次搜索 |

- **搜索并发数**：同时调度多少个视频源。
- **插件搜索并发数**：同时执行的插件类源（JS/Python 插件）数量上限；实际并发取它与"搜索并发数"中较小者。
- **总并发上限 / 单域名并发上限**：对应 OkHttp 的整体与单域名并发请求上限，是搜索速度的**真正瓶颈**（源多而域名集中时尤其明显）。
- **快速搜索批次大小**：聚搜模式下每批处理的源数量。

详细含义、各项之间的互相影响与调优建议见下文 [设置项说明](#设置项说明)。

### IJK 播放器设置

播放器设置 → IjkPlayer 分组下提供了以下可调项，均有合理默认值，不调整也能正常使用：

#### 缓冲大小（内存缓冲上限）

- **默认 / 2 / 4 / 8 / 15 MB / 无上限**，循环切换。默认优先使用接口配置（tv.json），接口未配置时取 **15MB**。
- **无上限（慎用）**：在 prepare 前下发 `infbuf=1`（player 类选项），read 线程不再等待队列满，会一直读到 EOF——暂停后也会持续缓存到整片结束，右上角缓存数字会持续增长到整片大小；代价是内存无上限（点播约等于整片大小，直播会一直涨到 OOM）。
- **15MB 是上限**：IJK 的 `max-buffer-size` 在 native 中的 AVOption 取值范围是 `[0, MAX_QUEUE_SIZE]`，实测本工程内置的 `libijkplayer.so` 为 `min=0 / max=15728640 / default=15728640`（即上限就是 15MB，且默认已是最大值）。超过 15MB 的值会被 AVOption 直接拒绝（`AVERROR(ERANGE)`）而不生效，因此设置项会对用户值做钳制。

效果：
- 播放中：read 线程会持续补数据，直到 packet 队列总字节达到该水位为止再停，缓冲越大越能容忍网络抖动。
- 暂停时：read 线程同样会继续填充到该水位后才停下（此时右上角速率归零属于正常现象），**这既是"暂停继续缓存"，也是它的上限**；因此暂停一段时间后看到的缓存大小会稳定在 ~15MB 左右，而不是设置里的几百 MB。
- 想把暂停后的可用缓存做到更大：只能在 native 层改 `MAX_QUEUE_SIZE`（需重新编译 `libijkplayer.so`）；把 `infbuf` 打开虽能绕过限制，但 read 线程会一路读到 EOF（整片进内存 → OOM），本版本不采用。

#### 磁盘缓存上限（CacheSize）

原"IJK 缓存"开/关项已升级为数值配置，用于 mp4 / mkv / avi 直链的边播边存：

- **关闭 / 256MB / 512MB / 1GB / 2GB / 4GB**，循环切换。
- **默认 2GB**，设置为 **关闭** 即完全不写磁盘。
- 落盘后同一地址复看、拖动进度都直接读本地，不用重新下载。

#### 卡死阈值（StallTimeout）

- **5 / 10 / 20 / 30 / 45 / 60 秒**，循环切换，**默认 30 秒**（小于 5 秒的无效值会自动回退为 30 秒）。
- 含义：播放中（非暂停、非缓冲）若持续无下载速度且播放位置完全不动，超过该时长即判定为卡死，自动重建连接并从原进度续播。
- 同一段播放最多自动恢复 3 次，之后不再自动重连，需手动切换源或重试——避免对持续异常的源无限重连。
- 想更快自愈可调小（如 10 秒）；网络较差、经常短暂无速度时可调大（如 60 秒）以减少误触发。

注意：HLS（m3u8）源仍主要靠内存缓冲，且不支持落盘（IJK 与 Exo 都未提供低成本方案）。

## 设置项说明

本节从"使用者"角度逐项说明设置页里的每个配置：它是什么、有哪些可选值、改动后什么时候生效。想了解背后的代码实现与配置项对应关系，可参考 [`doc/设置页配置项功能梳理.md`](doc/设置页配置项功能梳理.md)。

设置页分 **首页**、**播放器**、**系统** 三大类，另有 3 个二级弹窗：**播放器设置**、**搜索性能**、**按钮位置**。所有配置项默认值定义在 `App.java` 的 `initParams()` 中。

### 一、顶部区

- **配置地址**：填写 TVBox 接口地址（以及直播、EPG、代理地址），支持扫码用浏览器打开控制页。历史记录最多保留 20 条。修改后需要重新加载配置才会生效。
- **调试模式**：默认隐藏，仅开发者模式触发后才显示。开启后网络日志更详细、嗅探页面尺寸更大。注意：**每次重启 App 都会自动复位为"关闭"**。

### 二、首页

| 设置项 | 可选值 | 默认 | 说明 |
|---|---|---|---|
| 数据源 | 已启用的全部源 | — | 首页默认使用的接口源 |

### 六、搜索性能（弹窗）

集中管理影响搜索速度的 5 个参数（默认值都是最保守档位，可按设备性能上调）：

- **搜索并发数**：同时调度多少个源。只影响"把请求发出去的速度"，对最常见的普通接口源影响很小。
- **插件搜索并发数**：同时执行的插件类源上限；实际并发取它与"搜索并发数"中较小者，单把这一项调大通常无效。
- **总并发上限 / 单域名并发上限**：对应 OkHttp 的整体并发与"同一域名"并发上限。**这两项才是搜索速度的真正瓶颈**——很多采集源共用同一域名，此时无论"搜索并发数"调到多大，同一域名在飞的请求数都会被"单域名并发上限"卡住。
- **快速搜索批次大小**：聚搜模式下每批处理的源数量；批与批之间是串行的（要等本批全部返回才开下一批）。

调优建议：
- 想让搜索更快，优先上调 **单域名并发上限**（对"源多、域名集中"的情况收益最大）；上调前请确认源站能承受，过高可能触发限流或封禁。
- 遇到搜索变慢、个别源报错或设备发热时，改回默认值即可（5 / 5 / 64 / 5 / 50）。
- **总并发上限、单域名并发上限两项需重启 App 才生效**，其余三项下次搜索即生效。

### 九、深入解读：三个容易被忽略的设置项

下面三个设置项的实际行为比"开关"二字复杂得多，结合代码把内部机制讲清楚。

#### 9.1 广告过滤（实际是 m3u8 切片级净化）

- **生效逻辑**（`PlayFragment.java:683-749`）：开关 ON 时，对视频地址先判断是否满足 `URL 含 "://127.0.0.1/"` **或** `URL 含 ".m3u8"`，**满足任一即进入净化**（满足两者之一即可，并不是两个都要满足）。
- **完整判定表**：

  | 视频类型 | 含 `://127.0.0.1/` | 含 `.m3u8` | 是否净化 |
  |---|---|---|---|
  | 嗅探 m3u8（经本地代理） | ✅ | ✅ | ✅ |
  | 直链 m3u8 | ❌ | ✅ | ✅（也净化） |
  | 嗅探 mp4 等非 m3u8 | ✅ | ❌ | ✅ 触发净化但 M3U8.purify 返回 null → 自动回退原 URL |
  | 直链 mp4/mkv/avi | ❌ | ❌ | ❌ 旁路条件成立，跳过净化 |

  实操中**最常见是前两行**：嗅探 m3u8 和直链 m3u8 都会进净化；mp4/mkv/avi 直链彻底不进。
- **关闭时**：拿到地址直接 `startPlayUrl()`，原样播放，**和没装净化一样**。
- **开启且进入净化时**：先抓回 m3u8 文本，再调用 `M3U8.purify()` 做两轮清理：

  **第一轮：少数派剔除**（`M3U8.removeMinorityUrl`）

  1. 把所有 ts 切片按"文件名去掉后 4 字符"分组，找出出现次数最多的一组作为"主源"。
  2. 主源片数 < 总片数 80% → 切换为"按域名分组"再做一次。
  3. 域名最大占比仍 < 80% → **判定不了，放弃**（视频不连续，强行清理会丢正片）。
  4. 域名的最大占比 ≥ 80% 但每个域名都 ≥ 15 次 → 也放弃（都太多，没看出谁是广告）。
  5. 真正的清理：保留主域名（或主文件名组）的所有切片，把其它切片以及它紧邻的 `#EXTINF` 描述行一并删除。

  **第二轮：广告正则**（`M3U8.get() → VideoParseRuler.getHostsRegex()`）

  从 `tv.json` 的 `hostRuler` 字段里查该视频所在域名对应的正则规则（如 `#EXTINF:5.0`、`#EXT-X-DISCONTINUITY...15.0`），按规则扫描整个 m3u8，命中即整段 `#EXT-X-DISCONTINUITY...` 块删除。

  两轮中**第二轮命中即返回**，否则走第一轮；若两轮都没找到，仍然播放原 URL（不会卡死）。

- **典型案例**：
  - **多 CDN 混入**：某个站的 m3u8 大量切片在 `cdn-a.example.com`，少量 `cdn-b.example.com/ads/...` → 少数派剔除生效，`cdn-b` 那几段连同它的 `#EXTINF` 一起删掉，播放器请求时根本拿不到广告片。
  - **直链 m3u8 自带广告段**：源站直接返回的 m3u8 列表里混了广告 CDN → 一样会被少数派剔除或广告正则命中 → 实际看到的就是少等几十秒、前贴片消失。
  - **广告片段固定 5~15 秒**：用 `tv.json` 的 hostRuler 配 `"5.0"`、`"#EXT-X-DISCONTINUITY...30.0"` 等规则 → 正则扫描整段删除。
  - **站内嵌广告**：极端情况下广告片段和正片时长一致（30 秒 30 秒）→ 少数派剔除可能误删；此时关闭"广告过滤"更安全。
- **实际能看到的效果**：开启后，m3u8 流的开头/中间广告段不再加载，少等几十秒、广告前贴片消失。直播流几乎无效（直播切片一般不是固定时长）；mp4/mkv/avi 直链彻底不进净化流程（原 URL 直接播放）。

#### 9.2 安全 DNS（实际是给所有 OkHttp/IJK 请求套上一层加密 DNS）

- **工作原理**：
  1. `OkGoHelper.initDnsOverHttps()`（`OkGoHelper.java:130-158`）创建了一个**独立**的 OkHttpClient（带 10MB 缓存到 `cache/dohcache/`），用它作为 `DnsOverHttps.Builder().client(...).url(dohUrl)` 的传输层，构造一个 DoH 客户端。
  2. 该 DoH 客户端在主 OkHttpClient 构造时被 `.dns(dnsOverHttps)` 注入 → **所有 OkGo/OkHttp 请求的域名解析都改成走 DoH**，不再走系统 DNS。
  3. `ControlManager.java:117` 在启动本地嗅探代理的同时，调用 `IjkMediaPlayer.setDotPort(true, port)` → IJK 内部所有 URL 请求经过 `127.0.0.1:<port>` 走一遍，本地代理把 m3u8 子切片的解析也一并走 DoH。
- **切换时机**：在设置页选任意 DoH 选项，会立即 `dnsOverHttps.setUrl(...)` 并 `IjkMediaPlayer.toggleDotPort(pos > 0)`，**无需重启**（SettingActivity 会在对比后提示重启，但不是强制的）。
- **典型案例**：
  - **DNS 劫持**：运营商把返回 IP 替换成广告站，或返回 `0.0.0.0` 阻断访问 → 切 DoH（如"阿里"、"腾讯"）通常能解。
  - **DNS 污染**：某些视频域名被污染为错误 IP，需要走 Google (`8.8.8.8`)、Quad9 这类境外 DoH。
  - **隐私保护**：公共网络下运营商会记录所有 DNS 查询，DoH 全程 TLS 加密，避免被监听。
  - **小贴士**：如果你看到"明明网址对、但偶尔打开很慢或加载失败"，多半是 DNS 污染，DoH 一般就能解决。
- **注意点**：
  - 仅对 OkGo/OkHttp 主 client 生效；某些第三方库内部用自己的 DNS，不会被覆盖。
  - DoH 解析结果会缓存到本地（10MB），重启 App 后缓存保留。
  - 切换 DoH 时已建立的播放器连接可能没切干净，必要时重启 App 让所有连接统一走新 DoH。

#### 9.3 聚搜（实际是"边搜边看"的快速搜索页）

- **入口**（决定跳哪个页面，6 处判断）：
  - `SearchActivity.java:211/266/526/599/796`：搜索页"搜索按钮" / 点击搜索词 / 点击历史词 / 点击拼音联想词 → 开启则跳 `FastSearchActivity`。
  - `UserFragment.java:179`：首页用户点击搜索按钮 → 开启则跳 `FastSearchActivity`。
  - `GridFragment.java:265`：详情页二级分类的"站内搜索" → 开启则跳 `FastSearchActivity`。
- **`FastSearchActivity` 的 4 个区域**：
  - `mGridView`：搜索结果列表，按源聚合显示。
  - `mGridViewWordFenci`：分词联想（云端分词接口 `api.yesapi.cn/.../Scws.GetWords`，`FastSearchActivity.java:293`）。
  - `mGridViewFilter`：搜索完成后按"片名/演员/类型"过滤。
  - `mGridViewWord`：搜索词补全。
- **"边搜边看"怎么实现的**：
  - 后台用线程池（默认 5 个线程）+ **批次**（默认 50 源一批）跑所有勾选源。
  - 每个源完成时通过 `EventBus (RefreshEvent.TYPE_SEARCH_RESULT)` 推进度，标题实时显示 `已搜到 32 条 (5/12)` → `已搜到 56 条 (12/12) (搜索完毕)`。
  - **中途点开视频看 → 返回 → 已搜到的结果仍在** → 剩余慢源继续在后台补齐 → 体验"流式"出结果。
- **典型案例**：
  - 搜一个热门词（如"流浪地球"）：1 秒出 5 条结果 → 直接点开看；剩下几个慢源在后台继续搜；看完返回时列表已经补齐到几十条。
  - 搜一个生僻词（如小众纪录片名）：前 3 秒没有任何结果，先看着空列表等，3~10 秒陆续出来。
  - 想筛"只看 2024 年"：搜完后用 `mGridViewFilter` 按年份过滤。
- **和普通搜索（关闭时）的区别**：
  | 对比项 | 普通搜索（`SearchActivity`） | 聚搜（`FastSearchActivity`） |
  |---|---|---|
  | 进度提示 | 无 | 实时显示"X 条 (已搜/总源)" |
  | 边搜边看 | 不支持（搜完才进结果页） | 支持（结果陆续出现，可随时点开） |
  | 资源占用 | 较低（一次性出结果） | 较高（线程池 + EventBus 持续通信） |
  | 过滤/分词 | 简单 | 完整（带分词联想 + 多维度过滤） |
- **注意点**：
  - 关闭聚搜后回到传统单源结果页，体感是"全部源搜完才一次性出结果"。
  - 首次启用时建议在聚搜页重新勾选想要搜索的源（普通搜索勾选的状态不自动迁移）。
  - 仅"搜索"动作走聚搜，首页推荐/分类浏览不受影响。
